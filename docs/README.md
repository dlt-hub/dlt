# Documentation

## Set Up

You will need [uv](https://docs.astral.sh/uv/) and Node.js on your system. Then, from the `/docs` directory:

```sh
# Install Python dependencies (tools, linters, dlt itself)
make dev

# Install Node.js dependencies for the website
cd website && npm install
```

Run `make help` to see all available commands.

> Find info about the website build process at: `/docs/website/README`

## Sections

The documentation is composed of several sections:

- Static docs: found at `/docs/website/docs`, they are static `.md` files rendered as-is
- Dynamic docs: found at `/docs/website/docs`, they are `.md` files that included custom markers. During the build process, these markers are replaced by content. The processed docs land under `/docs/website/docs_processed`
- Python API reference: found at `/docs/website/docs_processed/api_reference`, these files are generated by `pydoc-markdown` from the Python source code under `/dlt`
- CLI reference: found at `/docs/website/docs/reference/command-line-interface.md`, this file is dynamically generated from an instantiated CLI instance. Note that the CLI auto-detects plugins, which can alter the available commands.
- Cookbook / examples: found at `/docs/website/docs/examples`, these `.md` files contain more sizeable code examples meant to be ran. They appear in a separate section of the rendered documentation.
- Educational notebooks: found at `/docs/education`, these jupyter (`.ipynb`) and marimo (`.py`) notebooks are not directly rendered in the docs, but are automatically listed in a separate docs section of the rendered docs. The marimo notebooks are automatically generated from the `.ipynb` files.

## Tools

The documentation development and build process relies on several tools. This gives a high-level overview of how things work.

- `make`: uses `docs/Makefile` to define simple command entrypoints for the user and other tools. Use `make help` to see all commands.
- `prek`: uses `.pre-commit-config.yaml` to define checks that are run before `git` commits or pushes. Use `prek list` to see all checks. Generally, `prek` calls the commands defined in `make` for consistency. An exception is made when the checks should run with different flags (e.g., different verbosity). `prek` checks are meant to only run when associated files are changed (e.g., run markdown formatter only if an `.md` file changed). On CI, all `prek` checks run for all files, ensuring consistency between dev and CI. You can do the same locally with `prek run --all-files`
- custom tools: under `/docs/tools/`, we have several custom Python scripts. Ideally, they use inline Python dependencies (PEP 723) to ensure isolated dependencies and can be ran with `uv run --script tools/TOOL.py`. These tools are primarily called by `make` commands. More complex tools should also have an associated `test_` file that will be verified.
- `mdsmith`: configured in `.mdsmith.yml`, it defines formatting and linting rules for `.md` files. This ensures consistency in the docs source files.
- `pytest-examples`: the file `/docs/test_snippets.py` leverages `pytest` with the plugin `pytest-examples` to lint, format, type-check, and run Python code snippets found in `.md` files. The file `/docs/conftest.py` implements the snippet collection logic and handles custom directive like `nolint`, `notype`, `execute`, `noexecute`, to include/exclude snippets for each check. The file `docs_snippets_stub.py` is used to simplify type-checking of snippets. These checks leverage `ruff` and `ty`, which are defined in `/docs/pyproject.toml`.

### `uv run lint-embedded-snippets`
Finds all embedded snippets in our docs, extracts them and performs the following checks:

* Snippet must have a valid language set, e.g. ```py
* Snippet must be parseable (works for py, toml, yaml and json snippets)
* Snippet must pass linting (works for py)
* Snippet must pass type checking with mypy (works for py)

This script is run on CI to ensure code quality in our docs.

### `uv run --script tools/preprocess_docs.py`
Copies the markdown files for the website from ./docs to ./docs_processed and performs various tasks underway, such as embedding snippets and inserting destination info into the destination pages. Is called by the npm script that previews and builds the website, and re-run on source changes by the `preprocess-docs` Docusaurus plugin during `npm run start`. Pass `--incremental` to keep the existing ./docs_processed folder and only rewrite files whose content changed.
