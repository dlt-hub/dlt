# Release highlights: 0.28

Released September 10, 2026, with `dlthub-client` 0.28.4. This release makes a workspace readable by coding agents as MCP tools, adds a workspace alerts API, and marks archived workspaces as read-only.

## Breaking changes

- **Upgrade the CLI to 0.28.4.** The minimum required CLI version moves to 0.28.4, so an older CLI is rejected with an upgrade message on every surface that checks the CLI version: the control-plane API and auth, and the data-plane API, logs and telemetry. Upgrade with `uv pip install -U "dlt[hub]"`, see [Installation](../getting-started/installation.md#upgrade-existing-installation).
- **List endpoints return a paginated object.** The public lists for organizations, organization workspaces, members, invites and API keys now return an object with `items`, `total`, `limit` and `offset` instead of a bare array. Third-party REST consumers need to read `items`. The web app ships updated in this release.

## Workspace access for agents

A coding agent can now ask what is deployed in a workspace, what ran, what it printed, what it configured, and what the pipelines did, through dlt's MCP server. Installing `dlthub-client` makes the tools available, and they stay off until you ask for them:

```sh
dlthub ai mcp run --stdio --features=+dlthub.jobs,+dlthub.logs,+dlthub.config,+dlthub.telemetry
```

See [`dlthub ai mcp run`](../command-line-interface.md#dlthub-ai-mcp-run) for the full command, and the [AI harness](../ai-harness/introduction.md) for how the pieces fit together.

## Alerts through the API

Workspace alerts can now be managed through the API as well as from the **Alerts** tab in workspace settings (see [email alerts](../notifications/email.md#dlthub-platform-alerts)). Both manage the same alerts. Each alert belongs to a trigger, such as `job-run-failure`, and carries one or more actions, such as sending an email:

- `GET /api/v1/triggers` lists the triggers you can alert on.
- `GET /api/v1/workspaces/{workspace_id}/alerts` lists a workspace's alerts, and `GET` or `DELETE` on `.../alerts/{trigger}` reads or removes one.
- `POST .../alerts/{trigger}/actions` adds an action to an alert, and `GET`, `PUT` or `DELETE` on `.../alerts/{trigger}/actions/{action_id}` reads, updates or removes one.

Reading alerts needs read access to the workspace, and changing them needs write access.

## Workspaces and settings

An [archived workspace](../pipeline-operations/what-is-a-workspace.md) is now visibly read-only: a banner appears on every one of its pages.

![The Overview page of an archived dltHub workspace, with the banner "This workspace is archived and read-only." across the top.](https://storage.googleapis.com/dlt-blog-images/dlthub-release-0-28-archived-workspace-banner.png)

Owners can still clean up [environment variables](../pipeline-operations/environment-variables.md) in an archived workspace, rather than hitting "Could not load the variables".

Permission cues across [settings](../platform-capabilities/settings.md) are consistent. Where an action is unavailable, a note names who can perform it, instead of the control being silently disabled, hidden, or replaced by an empty panel. The organization Members page explains the same way why inviting is unavailable until a [region](../platform-capabilities/regions.md) is set: owners get a note linking to General settings, where the region is chosen.

## Smaller improvements

- Any key-value field can be copied, with a copy button appearing on hover or keyboard focus.
- Collaborators no longer reach a dead end in onboarding: the skip action and the organization setup wizard are hidden from them, rather than prompting them to create a workspace they have no permission to create.
- The legacy per-workspace and organization settings pages, replaced by the centralized settings tree, now render the 404 page. Nothing in the product linked to them.
- Usage totals follow the range you selected. Switching the chart from Daily to Weekly or Monthly used to widen the period behind "Total Credits by Workspace" and "Credits by Instance Size". Only the chart snaps its start to a bucket boundary now.
- Redeploying no longer drifts an `every:` schedule. Shortening `every:1h` to `every:5m` left a job silent for the rest of the old hour, and redeploying without a schedule change pushed the next run one period further out each time. Cron (`schedule:`) jobs were never affected.

## For API consumers

`GET /scripts/{id}` accepts an optional `recent_runs_limit` parameter, which returns a job together with its most recent runs and their rows loaded in one request.

Note the pagination change in [Breaking changes](#breaking-changes) above: the public organization, workspace, member, invite and API key lists now return `items`, `total`, `limit` and `offset`.
