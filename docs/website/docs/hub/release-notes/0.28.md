# Release highlights: 0.28

Released September 10, 2026, with `dlthub-client` 0.28.4. This release gives every pipeline job its own page, adds tags for organizing jobs, makes a workspace readable by coding agents as MCP tools, and ships a Python SDK in alpha.

## Breaking changes

- **Upgrade the CLI to 0.28.4.** The minimum required CLI version moves to 0.28.4, so an older CLI is rejected with an upgrade message on every version-gated surface: the control-plane API and auth, and the data-plane API, logs and telemetry. Upgrade with `uv pip install -U "dlt[hub]"`, see [Installation](../getting-started/installation.md#upgrade-existing-installation).
- **List endpoints return a paginated object.** The public lists for organizations, organization workspaces, members, invites and API keys now return an object with `items`, `total`, `limit` and `offset` instead of a bare array. Third-party REST consumers need to read `items`. The web app and backoffice ship updated in this release.
- **Backoffice list parameters are renamed**, `search` to `q` and `created_after`/`created_before` to `start`/`end`, and the telemetry `list_schemas` filters accept repeated values.
- **`dlt_runtime.runtime_clients.*` is removed** from the CLI package with no compatibility shim. It was an internal path that was never a documented surface, and every `dlt runtime` command is unchanged, so this affects only code that imported the generated clients directly.

## A page for every pipeline job

Each [job](../pipeline-operations/overview.md) now has a detail page. It opens with the job's entry point, pipeline, [trigger](../pipeline-operations/triggers.md), schedule and [instance size](../pipeline-operations/job-configuration.md#instance-size), followed by a Run History chart and a Rows Loaded chart.

![A pipeline job detail page in dltHub, showing the job's entry point, pipeline, trigger, schedule and instance size above a Run History chart and a Rows Loaded chart.](https://storage.googleapis.com/dlt-blog-images/dlthub-release-0-28-job-detail.png)

Clicking a trigger in the header filters the runs listed below it.

The run history is a proper table, sortable and filterable by status, start time and duration, and each run links through to the pipeline runs it produced.

![The run history table on a pipeline job detail page, sortable and filterable by status, start time and duration, with each run linking to the pipeline runs it produced.](https://storage.googleapis.com/dlt-blog-images/dlthub-release-0-28-job-run-history.png)

`GET /scripts/{id}` gained an optional `recent_runs_limit` parameter, which returns a job together with its most recent runs and their rows loaded in one request.

:::info
The pipeline job pages ship behind a feature flag in this release.
:::

## Tags on jobs

A job declared with `expose={"tags": [...]}` shows its tags in the jobs list. Click one to filter to the jobs carrying it, and click several to narrow to the jobs carrying all of them.

![The dltHub jobs list with tag chips on each job and one tag selected, narrowing the list to the jobs carrying it.](https://storage.googleapis.com/dlt-blog-images/dlthub-release-0-28-job-tags.png)

Filters and sorting were reworked alongside them. You can filter by status, trigger, profile and tags, with the health signals leading the columns. The Trigger column now shows every way a job can fire rather than one of them, Last Run shows when the most recent run finished, and running jobs sort to the top. A paused job reads "Paused" in the Next run column instead of promising a scheduled time that cannot happen.

Filters, sorting and search live in the URL, so a filtered view survives a reload, sending the link to someone else, and navigating into a job and back. Long lists start with one chunk of rows and grow on an explicit **Show more**, in place of numbered pages.

## Your workspace, readable by agents

A coding agent can now ask what is deployed in a workspace, what ran, what it printed, what it configured, and what the pipelines did, through dlt's MCP server. Installing `dlthub-client` makes the tools available, and they stay off until you ask for them:

```sh
dlthub ai mcp run --stdio --features=+dlthub.jobs,+dlthub.logs,+dlthub.config,+dlthub.telemetry
```

See [`dlthub ai mcp run`](../command-line-interface.md#dlthub-ai-mcp-run) for the full command, and the [AI harness](../ai-harness/introduction.md) for how the pieces fit together.

An **Agents** section also appears in the workspace sidebar, behind the `agents-section` feature flag.

## A Python SDK, in alpha

The CLI now bundles a dltHub Python SDK with typed domain objects for workspaces, jobs, organizations, deployments, configurations, runs, dataplanes and variables, with lazy paging. It is unpublished for now, so the surface can still change before it is documented and supported.

## Workspaces and settings

An [archived workspace](../pipeline-operations/what-is-a-workspace.md) is now visibly read-only: a banner appears on every one of its pages.

![A dltHub workspace page carrying the banner that marks the workspace as archived and read-only.](https://storage.googleapis.com/dlt-blog-images/dlthub-release-0-28-archived-workspace-banner.png)

Owners can still clean up [environment variables](../pipeline-operations/environment-variables.md) in an archived workspace, rather than hitting "Could not load the variables".

Permission cues across [settings](../platform-capabilities/settings.md) are consistent. Where an action is unavailable, a note names who can perform it, instead of the control being silently disabled, hidden, or replaced by an empty panel. The organization Members page explains the region gate the same way: owners get a note linking to General settings, where the [region](../platform-capabilities/regions.md) is set.

## Smaller improvements

- Any key-value field can be copied, with a copy button appearing on hover or keyboard focus.
- `workspace list`, `workspace info` and `workspace connect` now work when you authenticate with a workspace API key, instead of failing with a 403.
- Collaborators no longer reach a dead end in onboarding: the skip action is hidden and the organization setup wizard is gated, rather than prompting them to create a workspace they have no permission to create.
- The legacy per-workspace and organization settings pages, replaced by the centralized settings tree, now render the 404 page. Nothing in the product linked to them.
- Usage totals follow the range you selected. Switching the chart from Daily to Weekly or Monthly used to widen the period behind "Total Credits by Workspace" and "Credits by Instance Size". Only the chart snaps its start to a bucket boundary now.
- Redeploying no longer drifts an `every:` schedule. Shortening `every:1h` to `every:5m` left a job silent for the rest of the old hour, and redeploying without a schedule change pushed the next run one period further out each time. Cron (`schedule:`) jobs were never affected.

## For API consumers

A workspace alerts API lets you manage alerts per workspace against canonical trigger identifiers, with a catalog for discovering what can be alerted on: `GET /api/v1/triggers` and `GET|PUT|DELETE /api/v1/workspaces/{workspace_id}/alerts[/{trigger}]`.

Note the pagination change in [Breaking changes](#breaking-changes) above: the public organization, workspace, member, invite and API key lists now return `items`, `total`, `limit` and `offset`.
